### Fixed
- Messages: a paging that Smartschool restarted halfway ended as after the last page, so `getAllHeaders` and `getAllArchiveHeaders` returned part of the box without telling (#76). Smartschool keeps the paging position per user and box, not in the session as the docs of #15 said, and restarts it on every `message list` of the box in any session of the account: a `getHeaders` (also in poll mode) or another paging of the box on the same client, a listing by another client or app (such as another tool call of smartschool-mcp), or the user opening the box in the web client. The next `continue_messages` then answers with the second page again; `getHeaderPages` found no new header in it and ended. Now:
  - `getHeaderPages` and `getArchiveHeaderPages` fail there with the new `SmartschoolPagingRestartedError` (extends `SmartschoolException`, exported with the other errors), after the pages they emitted, and `getAllHeaders` and `getAllArchiveHeaders` throw it rather than return a short list, so that the caller can list the box again. It is not a `SmartschoolSessionExpiredError`: the session is fine;
  - a restart is recognised by a page that holds headers, all of them emitted already. An answer without headers still ends the paging normally, also when it announces more: a box that is an exact multiple of the page size may get one last (not checked live). A server that repeats a page now fails the same way instead of ending the paging.

  Verified live (read-only, on an inbox of 186 headers, with two clients that each had a cookie cache and so a session of their own): after a `message list` of the box by the second client, the first one's next `continue_messages` answered with its second page again, 50 headers it had already, still announcing more. A new login between two pages (the cookies cleared, a `401`, a full login with 2FA) went on with the next page, so a login does not restart the paging. The `message list` answer holds no total for the box, so a listing cannot be checked against one. Not covered by the error: two pagings of the same box at the same time share the one position, so one can skip the pages the other got while every header it gets is new to it; within one client the next entry (#80) prevents it, and across clients the docs say so. The doc comments of `getHeaderPages` and `getAllHeaders`, the README and the #15 entry of 0.3.0 are corrected. Tested offline, among others against a fake Smartschool that keeps one position per box for the account, with the box listed by a second client halfway through a `getAllHeaders`.
- Messages: two pagings of the same box on one client could skip each other's pages without an error (#80). Smartschool keeps one paging position per user and box (#76), which every `message list` of the box restarts and every `continue_messages` moves on, whichever paging sent it. Once pagings A and B had both listed the box, A's next page took B's second page, and B went on with the third: every header B got was new to it, so the check of #76 did not see the gap. The client now keeps count of the `message list` and `continue_messages` requests of each box (box type and box ID), for all the `MessagesService`s of the client, since they share its account:
  - `getAllHeaders` and `getAllArchiveHeaders` of a box run one at a time: a call waits for the calls of the box that started before it, so two calls at the same time both get the whole box. They read their pages themselves, so the wait always ends;
  - `getHeaderPages` and `getArchiveHeaderPages` wait for those too before their first request, but make a later paging of the box wait for their first page only, not for their end. Their listener decides when the next page is asked for, so a lock held for the life of the stream would hang a listener that waits for another paging of the box (`await for (final page in messages.getHeaderPages()) { await messages.getAllHeaders(); }`), and a listener that stops without cancelling would hold the box for ever; a timeout would only make that hang shorter. The later paging goes ahead instead, and the stream fails with `SmartschoolPagingRestartedError` at its next page, before it asks Smartschool for it;
  - `getHeaders` (also in poll mode, as `refreshHeadersIncremental` sends it) still never waits, but makes a paging of the box that runs fail the same way at its next page, since it restarted the position. When it went out while a page was being asked for, the paging fails without emitting that page: Smartschool may have answered it from the other listing;
  - a paging waits for the requests of the box on their way to be answered before it sends its `message list`, so that none of them reaches Smartschool after it.

  So within one client a paging no longer skips pages without an error; the error of a paging cut short on the client says that the box was listed again on this client. Across clients, sessions and apps nothing can see a listing coming: there the check of #76 applies, and two pagings of the same box at the same time can still skip each other's pages, as the docs say. The doc comments of `getHeaders`, `getHeaderPages`, `getAllHeaders`, their archive variants and `SmartschoolPagingRestartedError`, and the README, are updated. Tested offline against the fake Smartschool of #76 that keeps one position per box for the account (it now also follows the sort order of the box's last `message list`, which is assumed, not checked live): the interleaving of the issue, two `getAllHeaders` at once (also on two services of the client), a `getHeaderPages` behind a running `getAllHeaders`, a `getAllHeaders` in the listener of a `getHeaderPages` of the box (it ends, and the paging fails, rather than hang), a listener that pauses for good, a `getHeaders` between two pages and while a page is asked for, pagings of two boxes in turns, a `getAllHeaders` that fails or stops at `limit` and lets the next one go, the archive, and a listing on another client.

- Auth: a TOTP secret (`mfa`) that was not plain Base32 failed the login with a bare `FormatException` of the `otp` package, wrapped in a `DioException` (and so not unwrapped by the request methods), after the password had been posted (#79). Two easy ways to get there: the key copied in groups, as an authenticator setup screen shows it (`JBSW Y3DP EHPK 3PXP`), or the 6-digit code of the authenticator app typed instead of the key. Callers could not tell it from any other failure, nor tell the user to check the key, and every login posted the password again. Now:
  - white space (also tabs, line breaks and non-breaking spaces) and hyphens in the secret are ignored, as are lower case and `=` padding at the end (as before): a key copied in groups logs in, with the code of the key;
  - a secret that is still not a key fails the login with the new `SmartschoolInvalidTotpSecretError` (extends `SmartschoolAuthenticationError`, exported with the other errors): empty once white space and hyphens are removed (such as `-`), a character other than the letters A-Z and the digits 2-7 (with `=` only at the end), or only digits, such as the 6-digit code. Like the other login failures (#11, #20) it is thrown as itself by `ensureAuthenticated()`, `platformId` and every service call, and only a request on `client.dio` gets it wrapped (as the `error` of the `DioException`). Its message says to use the key, not the code, and never holds the secret;
  - an `mfa` that is empty or only white space is still no `mfa` at all, as before: an account without 2FA (a pupil's) logs in with it, a 2FA step throws `SmartschoolTwoFactorRequiredError` and an account verification `SmartschoolAccountVerificationRequiredError`;
  - the check runs **before the password is posted**, when `mfa` is not a date (`yyyy-mm-dd`, the account-verification answer) and not empty once trimmed, since such an `mfa` can answer neither step after the password: the login neither loads the login form nor posts the password, and does not count toward the limit on logins in a row (#31), so every request that needs a login fails the same way, at once, until the credentials are fixed. Only the request that found the session cold went out (for a GET, with the redirect to the login page that the HTTP client follows itself). This holds for an account that would ask for neither step too, which used to log in with such an `mfa` (unused): set `mfa` only to a date or a TOTP secret;
  - an `mfa` that is a date passes that check and is posted as the account-verification answer as before; when Smartschool asks for a 2FA code instead, it fails at the 2FA step with the same error, after the password but before any request of that step, and counts as rejected credentials: after three such logins the client does not log in again after its cooldown, until `resetLoginAttempts()` (#32);
  - the new static `Credentials.normalizeTotpSecret(key)` runs the same check without a client, for instance where a user enters the key: it returns the key as the login uses it (without white space and hyphens, upper case, no padding), or throws the `SmartschoolInvalidTotpSecretError`.

  So a caller no longer needs a check of its own: it can drop its own normalising and validating of the key, map `SmartschoolInvalidTotpSecretError` to "check the 2FA key" and treat it as permanent (the client sends nothing of the login for it, so retrying does not cost a password login), and use `Credentials.normalizeTotpSecret` to check a key before it is saved (smartschool-mcp's workaround, yvanvds/smartschool-mcp#34). Tested offline, against the fake login chain: a key in groups (spaces, hyphens, lower case with padding) logs in and posts the code of the key; the 6-digit code and a key with a `1` fail before the password, also four times in a row; a date fails at the 2FA step before its requests; an `mfa` of only white space (spaces, a tab and line break, a non-breaking space) logs in on an account without a second step and is a `SmartschoolTwoFactorRequiredError` at a 2FA step.

- Downloads: `maxBytes` did not limit what came in before the stream of a download was listened to (#81). Dio reads the answer to a download from the moment its headers are in, and keeps what comes in in memory until its body is listened to. `SmartschoolClient.downloadStream` (and so `IntradeskService.downloadFileStream` and `MessageAttachment.downloadStream`) took the body over, and started counting its bytes against `maxBytes`, only once the caller listened to `SmartschoolDownload.stream`. A caller that listened a moment late, such as one that pipes the stream into `File.openWrite()` (which listens once the file is open), could so hold the whole file in memory, however much larger than `maxBytes`, when Smartschool sent no `Content-Length`. Seen in smartschool-mcp's CI on a slow runner (yvanvds/smartschool-mcp#36); in the issue's reproduction a 17 MiB file with a `maxBytes` of 1 MiB came in whole in the 300 ms before the stream was listened to, which then gave 1 MiB and the error. The docs only said to listen right away. Now the client takes the body over as soon as the headers are in, and holds it until the stream is listened to:
  - until then the transfer waits, as while the stream is paused: no more of the content comes in than the few chunks that arrived while the client handled the headers (three of 64 KiB in the tests), with or without `maxBytes`, and none of it is lost;
  - every byte counts against `maxBytes`, also one that came in before the stream was listened to, so the transfer, and what the client holds of it in memory, stays within `maxBytes` and a few chunks, whenever the stream is listened to. A larger announced size still fails before anything is read, and the stream still ends with the `SmartschoolDownloadTooLargeError` after at most `maxBytes` bytes;
  - a download that is neither read nor cancelled keeps its connection open (Dio used to read it to its end into memory): read its stream or call `cancel()`, as the docs already asked. A `receiveTimeout` set on `client.dio` counts the wait for the reader, as it counts a pause. `download`, `downloadFile` and `MessageAttachment.download` read the stream at once and are unchanged.

  So a caller can rely on `maxBytes` as a limit on the whole transfer and on the memory it takes, and need not listen to the stream right away: it may open the file it writes to first and pipe the stream into it afterwards (smartschool-mcp's `writeDownload` opens the file first, and needs no change). The doc comments of `downloadStream` and `SmartschoolDownload`, and the README, now say so instead of "listen to it right away". Tested offline: the issue's 17 MiB file without `Content-Length`, sent in chunks of 64 KiB as a connection sends them (none while paused), through `IntradeskService.downloadFileStream` with a `maxBytes` of 1 MiB and a reader 300 ms late (before the fix all 17,825,792 bytes came in; now 196,608 before the reader listened, the stream gave 1,048,576 bytes and the error, and the transfer stopped at the chunk that went past the limit, 1,114,112 bytes sent in all); the same file of 4 MiB without `maxBytes` (a few chunks, then the whole file once read); a `cancel()` before listening; a `receiveTimeout`; and over a real connection on loopback, a body of 64 MiB with a reader 300 ms late that pipes it into a file (before the fix the server sent all of it; now it could only fill the buffers of the connection, and the file got at most `maxBytes`).

- Package: the published package no longer contains `PROJECT_OVERVIEW.md`, a local developer notes file that 0.3.1 shipped by mistake. It is in `.gitignore`, but pub reads only `.pubignore` when that file exists, so `.pubignore` now lists it too. The file held no credentials or personal data.

## 0.3.0 - 2026-10-01

### Breaking changes
This release changes what several calls throw or return. It is 0.3.0 rather than 0.2.11 so that a `^0.2.x` constraint does not pick it up unnoticed. The entries below give the details; when upgrading, check:
- **Errors from requests.**
  - Smartschool being unreachable is a `SmartschoolConnectionError`: from `ensureAuthenticated()` instead of a `SmartschoolAuthenticationError` (#10), and from every service call instead of a raw `DioException` (#21).
  - A login failure during a service call is thrown as itself instead of wrapped in a `DioException` (#20).
  - Reaching the login-attempt limit is a `SmartschoolSessionExpiredError` (#31, #32).
  - `PresenceService` tells an expired session (`SmartschoolSessionExpiredError`) apart from a refused Presence request (#5).
  - A client used after `dispose()` throws a `StateError`, which an `on SmartschoolException` clause does not catch (#54).
- **`sendMessage` / `sendReply` outcome.**
  - A submit that Smartschool does not confirm throws `SmartschoolSendUnconfirmedError` instead of returning normally. The message may have been sent, so don't resend it blindly (#25).
  - The steps of a send are no longer retried after a new login, and a step in another session fails before it is sent (#25, #38).
  - A recipient Smartschool does not register stops the send with a `SmartschoolComposeError` (#39).
  - Setting a deprecated `MessageSendOptions` field throws an `ArgumentError` (#43).
- **Record shapes.** `getReplyAllRecipients`, `parseReplyAllRecipients`, `getSentMessageRecipients` and `parseSentMessageRecipients` return `(to, cc, bcc)` instead of `(to, cc)` (#33).
- **Types.** `IntradeskListing.weblinks` is a `List<IntradeskWeblink>` instead of a list of maps (#37).
- **Values.**
  - Recipient names of a sent-box message no longer start with `+`/`-`; see `FullMessage.toRecipients` and the other recipient lists for the read state (#34).
  - `getMessage` returns `null` for an ID the box does not hold (#16).
  - `moveToTrash` reports a moved message as deleted, and returns `null` when nothing was deleted (#19, #59). Prefer the new `moveToTrashFrom` (#60, #61).

### Added
- Auth: typed login failures (#11). Each login failure is now thrown as its own subclass of `SmartschoolAuthenticationError`, so callers can match on the type instead of on the message text:
  - `SmartschoolInvalidCredentialsError` — the username or password is rejected (also SSO-only accounts);
  - `SmartschoolTwoFactorRequiredError` — Smartschool asks for a 2FA code, but `mfa` holds no TOTP secret;
  - `SmartschoolTwoFactorRejectedError` — the 2FA code is rejected;
  - `SmartschoolUnsupportedTwoFactorMethodError` — the account's 2FA does not offer an authenticator app; `availableMethods` lists what it does offer;
  - `SmartschoolAccountVerificationRequiredError` — Smartschool asks for account verification (date of birth), but `mfa` is empty or not a date;
  - `SmartschoolAccountVerificationRejectedError` — the account verification answer is rejected.

  Backwards compatible: they extend `SmartschoolAuthenticationError` and keep the previous messages, so existing `catch` clauses and message checks keep working. The base class is still thrown for the other authentication failures (an unrecognised login step, HTML where data was expected); reaching the maximum number of login attempts is a `SmartschoolSessionExpiredError` since #31 (see below).
- `SmartschoolConnectionError` (extends `SmartschoolException`): Smartschool cannot be reached. Carries the underlying error as `cause`.
- `SmartschoolSessionExpiredError` (extends `SmartschoolAuthenticationError`): Smartschool does not accept the session for a request, also after the client logged in again where it could (#5). The request was not carried out, so the remedy is to sign in again and retry. Thrown by every request method of `SmartschoolClient`, and so every service, when the retry of a request after logging in again is still answered with `401` (#8) or by the login chain (#22, see below), and, without logging in, when the client has stopped logging in again after three logins in a row that did not get the session accepted (#31, see below).
- `SmartschoolClient.postFormResponse(path, fields, {query})`: the same POST as `postFormRaw`, returning the whole `Response<String>` (status code, headers, final URL) instead of only the body.
- Messages: headers beyond the first 50 of a box (#15). `getHeaders()` and `getArchiveHeaders()` return one page: at most 50 headers, the newest 50 by default, and Smartschool's `message list` takes no offset. Its web client loads the rest while the user scrolls down: an answer that has more ends with a `continue_messages` action, and a `postboxes / continue_messages` request (with `boxID`, `boxType` and `layout`) then answers with the next page, in the same order, until the last page ends with `rebuildfinish`. The new methods do the same:
  - `getHeaderPages({boxType, boxId, sortBy, sortOrder})` and `getArchiveHeaderPages({boxId, sortBy, sortOrder})` return a `Stream<List<ShortMessage>>` of the pages. The first is what `getHeaders` returns; each next page is requested only when the listener wants it, so `take`, `takeWhile` or cancelling the subscription stops the paging without fetching the rest of the box. The stream ends after the last page, and also at a page that brings no header it has not emitted yet, so a server that repeats a page cannot keep it going; a header already emitted is left out of later pages, and no page is empty.
  - `getAllHeaders({boxType, boxId, sortBy, sortOrder, limit})` and `getAllArchiveHeaders({boxId, sortBy, sortOrder, limit})` collect those pages: every header of the box, or the first `limit`, without requesting further pages once they are in.

  Smartschool keeps the paging position in the session, one per box, and restarts it on every `message list` of that box (also in poll mode), so listing a box while it is being paged ends that paging early; paging different boxes at once is fine. (Corrected in 0.3.2, #76: Smartschool keeps the position per user and box, not in the session, so a listing of the box in any session of the account restarts it, and a restarted paging fails with `SmartschoolPagingRestartedError` instead of ending early.) Verified live on a teacher account: the inbox, the sent box and the archive each returned 50 headers through `getHeaders`, and 191, 471 and 1437 through `getAllHeaders` (also in ascending order), with no duplicates. The existing methods are unchanged: a page API over Smartschool's cursor would have to replay every earlier page for each call, and a page fetched in a separate call can shift when a message arrives in between.
- Messages: the read state of each recipient of a sent message (#34). For a message in the sent box, Smartschool starts every recipient name of `show message` with `+` or `-`, which `getMessage` passed through in `FullMessage.receivers`, `ccReceivers` and `bccReceivers` without saying what it was. It is the recipient's read state: `+` when the recipient's copy of the message is read, `-` when it is unread. Smartschool's web client removes the marker when it shows a message of the sent box and marks the recipients with `-` as `userNotRead`; verified live (read-only) on the 150 newest messages of a teacher's sent box: all 726 recipient names carry a marker, and for each of the 13 messages with the user among their recipients, the user's marker matched the read state of the user's own copy (in the inbox, the archive or the trash): 10 times `+` and read, 3 times `-` and unread. New API:
  - `MessageRecipient`, with the `name` and `hasRead` (`bool?`) of a recipient, and `MessageRecipient.fromSentBoxName(raw)`, which reads one name as the sent box gives it (a name without a marker is kept, with `hasRead` `null`);
  - `FullMessage.toRecipients`, `ccRecipients` and `bccRecipients`: the recipients of each field, in the order of `receivers`, `ccReceivers` and `bccReceivers`, with `hasRead` set for a message in the sent box and `null` in every other box, where Smartschool gives no read state. The `FullMessage` constructor takes them as optional parameters; without them, they are derived from the names, with `hasRead` `null`;
  - `FullMessage.fromXml(xml, {boxType})`: the box the message was requested from (default `BoxType.inbox`), which `getMessage` passes. The marker is read only for `BoxType.sent`, as Smartschool's web client does.
- Messages: `MessagesService.getReplyRecipients(msgId, {boxType})`, the recipient of a plain reply with their user ID (#24). It loads Smartschool's reply form (`composeType=1`, the form its Reply button opens), which names the sender of the message, and returns `(to, cc, bcc)` like `getReplyAllRecipients`: the sender in `to`, with `cc` and `bcc` empty. `getReplyAllRecipients` also lists the sender, but among the other To recipients, in no fixed place and not marked, so a caller could only pick it out by comparing display names. The reply form names the sender whoever it is: for a message in the sent box, and for one the user sent to themselves, that is the user. Verified live (read-only) on 12 read inbox messages, one in the archive and two in the sent box: each reply form named exactly one recipient, in To, with the user ID, `ssId` and `userLt` of one of the reply-all form's To entries (of the seven messages with several To recipients, the last entry in six and the first in one); for the message the user sent to themselves and for the sent messages, the user. The doc of `getReplyAllRecipients` no longer says that the user is always left out: its form names the user as the sender of a message they sent to themselves.
- Messages: `MessagesService.sendReply(msgId, params, {boxType, all})`, a reply that Smartschool links to the message it answers (#26). `sendMessage` always submits the new-message form (`composeType=0`, `msgID=undefined`, `origMsgID` `0`, `composeAction` `0`), so a reply sent with it was a new message, linked to the original by its `Re:` subject only. `sendReply` loads the message's reply form instead (`composeType=1`, or with `all: true` the reply-all form, `composeType=2`, both with `msgID=<id>`), which carries `origMsgID=<id>` and `composeAction=2`, and submits it as Smartschool's web client does: to the URL it was loaded from (the form's `action` is empty; the compose script sets `send=send` and submits it), with the form's own hidden fields and tokens. It fails with a `SmartschoolComposeError`, before anything is registered or submitted, when Smartschool does not answer with the reply form of that message (the box does not hold it). Everything else is `sendMessage`'s: recipients registered with the form's `uniqueUsc`, attachments uploaded to its `randomDir`, the send confirmed only by the answer that closes the compose window, and no step after loading the form retried after logging in again (#25). The reply form comes with its recipients (the sender, or everyone the reply-all form names) already registered on it: the compose script sends nothing for them when the page loads, and registers only the recipients the user picks from its search, where Smartschool's answer marks each result as selectable or not; what Smartschool does with a second registration of a recipient was not checked. `sendReply` therefore does not register again a recipient that the form names in the same field of `params` (same `userId`, `ssId` and `userLt`), and registers the others as `sendMessage` does. Taking a recipient off the form is not supported: when `params` leave out a recipient that the form names, `sendReply` throws a `SmartschoolComposeError` naming it, before anything is registered, so a reply never goes to a recipient the caller did not list; pass the lists of `getReplyRecipients` (or `getReplyAllRecipients` with `all: true`) as they are, with more recipients if needed. Since #42, `sendReply` takes such a recipient off the form instead (see below). The subject and body are sent as given; the quote of the message that the form starts with is not added. A dedicated method rather than a reply field on `SendMessageParams`: the reply target (message, box, reply or reply all) picks the form, like the `msgId`/`boxType` of `getReplyRecipients` and `getReplyAllRecipients`, while `SendMessageParams` keeps describing the message itself, and `sendMessage` is unchanged. Tested against a fake Smartschool only: the live submit of a reply is untested (a live test may not send), and whether Smartschool then marks the message as answered (`hasReply`) is not verified.
- Messages: `MessagesService.sendReply` takes a recipient that the reply form names and `params` leave out off the form, instead of refusing the reply (#42). The reply form comes with the recipients of the reply registered on it (the sender, or with `all: true` everyone the reply-all form names), and `sendReply` threw a `SmartschoolComposeError` when `params` left one of them out of its field, so a caller could not, for example, reply to all without one of the recipients, or reply to all to their own sent message without themselves. It now takes each such recipient off the form first, as the × of the recipient in Smartschool's web client does (`oSearchUsers.deleteReceiverSpan` in its compose script): a form-urlencoded `deleteUsersFromSelected` with `xml=<users><user><type>…</type><userid>…</userid><ssid>…</ssid><userlt>…</userlt></user></users>`, from the entry's `typeatt` (the field, also a co-account field), `idatt` (the user ID with its `U` prefix), `ssidatt` and `userltatt`, and the form's `uniqueUsc`. Like the other steps after loading the form, it is not retried after logging in again and goes out only in the session the form was loaded in (#25, #38). A recipient that `params` move to another field is taken off its field and then registered in the other, as the web client's drag and drop does. Checked live on the reply form of a message the account sent to itself, which was then abandoned (never submitted), with the account's own user only: Smartschool answers a removal with HTTP `200` and XML that lists the entries it took off (`<users><user>` with the `type`, `ssID`, `userID` and `userLT` that were asked for), and an entry the form does not have (taken off already, asked for in another field, or with the user ID without its `U` prefix) with `200` and an empty list (`<users />`). After a removal, registering the user again in that field is accepted (while the form names it, Smartschool answers that with an empty body, #39), and so is registering it in another field. Each answer is now checked for the entry that was asked for; when it does not list it, the send stops with a `SmartschoolComposeError` that names the recipient and its field, before the other recipients, the attachments and the submit: nothing was sent. Tested against a fake Smartschool that answers as the live platform did; the live submit of a reply is still untested. **Behaviour change:** a reply whose `params` leave out a recipient that the form names is sent without that recipient, instead of failing with a `SmartschoolComposeError`.
- Messages: a send can choose the compose form's own options (#47): store the message in the LVS, and a delayed send. `sendMessage` and `sendReply` always submitted Smartschool's compose form with its defaults for them (`copyToLVS=dontCopyToLVS` and an empty `sendDate`), so a caller could neither store a message in the LVS nor schedule it. `MessageSendOptions` has two new fields, submitted in the form's own fields by both methods:
  - `lvsCopy`, an `LvsCopy`: `none` (the default, `dontCopyToLVS`, the option the form selects), `store` (`copyToLVS`) or `storeConfidential` (`copyToLVSAndMarkAsPrivate`), the options of the form's `copyToLVS` select, the same on the new-message and reply forms (the recorded forms, and the live forms checked with a GET only). An option other than `none` is sent only when the loaded form offers it; Smartschool leaves the select out for an account that may not store messages in the LVS, and the send then throws a `SmartschoolComposeError` before registering any recipient (nothing was sent);
  - `sendAt`, a `DateTime?` (default `null`, send now): a delayed send, as the "Uitgesteld versturen" dialog of Smartschool's web client (`Messages/desktop/delayedMessages`) schedules it. The dialog writes the chosen time into the form's hidden `sendDate` field with date-fns `formatISO` (ISO 8601 in the local time, to the second, with the UTC offset, e.g. `2026-10-02T07:30:00+02:00`) and then submits the form as for a send now, with no other field; `sendAt` is submitted the same way, in the local time of the machine (the same instant whatever the time zone of the `DateTime`, milliseconds dropped). As the dialog does, a time that is not after now, or later than the end of the same day next year (the last day its date picker offers), is refused with an `ArgumentError` before any request, and the form must offer a delayed send (its `sendDate` field, and `isScheduledMessagesEnabled` in its `SMSC.vars`, without which the web client's send button does not fill `sendDate`), or the send throws a `SmartschoolComposeError` before registering any recipient. The web client counts a scheduled message in the scheduled box (`BoxType.scheduled`); a `SmartschoolSendUnconfirmedError` of a delayed send says to check that box.

  The defaults are unchanged. Not verified with a real send, which the tests never make: Smartschool's answer to the submit of a scheduled message (it counts as sent only when it is the answer to a sent message, `200` and `window.close()`, #25; another answer is a `SmartschoolSendUnconfirmedError`), whether Smartschool reads the offset of a time outside Belgium's time zone, and what it does with an LVS copy (for instance of a message to recipients who are not pupils).

- `SmartschoolSendUnconfirmedError` (extends `SmartschoolException`): `MessagesService.sendMessage` submitted the message, but Smartschool's answer does not confirm that it was sent, or no answer came in (#25, see Fixed below). The message may or may not have been sent: check the sent box before sending it again. Carries the HTTP `statusCode` of the answer, or the `cause` (typically a `SmartschoolConnectionError`) when none came in. Deliberately not a `SmartschoolComposeError`, which now only means that the compose form could not be used and nothing was sent.
- `SmartschoolClient.postMultipartResponse(path, formData, {retryAfterLogin})`: the same POST as `postMultipartRaw`, returning the whole `Response<String>`. `postMultipartRaw`, `postMultipartResponse`, `postFormRaw` and `postFormResponse` take `retryAfterLogin` (default `true`): pass `false` for a request that carries state of the session it was prepared in, such as the tokens of Smartschool's compose form. When Smartschool refuses the session for such a request, it is neither retried nor used to log in again: it fails at once with a `SmartschoolSessionExpiredError` (the request was not carried out), and the next request that Smartschool refuses logs in (#25).
- `SmartschoolClient.getResponse(path, {query})`: the same GET as `getRaw`, returning the whole `Response<String>`. `postFormRaw`, `postFormResponse`, `postMultipartRaw` and `postMultipartResponse` take `sameSessionAs`, such an earlier answer of the client, for a request that carries state of that answer's session (such as the compose form's tokens) and must go out only in that session: when a login started on the client since that answer's request went out, or one runs, for whichever request, the request is not sent and fails at once with a `SmartschoolSessionExpiredError` (#38, see Fixed below).
- `SmartschoolClient.cacheDir` and `SmartschoolClient.defaultCacheDir(username)`: the per-user cache folder (#30). A client keeps its per-user data (the saved session cookies, in `.cookies`) in the `cacheDir` given to `create`, or by default in `.cache/smartschool/<username>` in the user's home folder (`HOME`, else `USERPROFILE`, else the current directory), but did not say which folder that was, so an app that keeps its own per-user data next to the library's had to repeat that rule, and a copy would drift if the default changed. `cacheDir` is the folder a client uses, exactly as given to `create` or the default one; the static `defaultCacheDir(username)` is the default folder for a username without a client (it only works out the path and does not create the folder). `create` is unchanged: it uses the same folder as before and still makes it when it does not exist.
- Downloads: a size limit and a streaming download (#41). `SmartschoolClient.download(path)`, and so `IntradeskService.downloadFile(fileId)` and `MessageAttachment.download(client)`, read the whole answer into memory, so a caller could not refuse a file above a size (Intradesk files go up to hundreds of MB), stop a download partway, or read it as a stream, and did not see the size or name Smartschool gives the file. Backwards compatible: the existing methods keep their signatures and behaviour, with a new optional parameter.
  - `maxBytes` on `download`, `downloadFile` and `MessageAttachment.download`: the download fails with the new `SmartschoolDownloadTooLargeError` (extends `SmartschoolException`; carries `maxBytes` and the announced `contentLength`) as soon as the file turns out larger: at once when Smartschool announces a larger size (`Content-Length`), otherwise once more than `maxBytes` bytes came in. The client then stops the transfer. The size in an Intradesk listing may be out of date; this checks the file itself.
  - `SmartschoolClient.downloadStream(path, {maxBytes})`, `IntradeskService.downloadFileStream(fileId, {maxBytes})` and `MessageAttachment.downloadStream(client, {maxBytes})` return the new `SmartschoolDownload` as soon as the headers are in: `contentLength`, `fileName` (from `Content-Disposition`, `filename*` in UTF-8 or ISO-8859-1 before `filename`), `contentType`, `headers`, and the content as a `Stream<List<int>>` read as it comes in (it pipes into `File.openWrite()`). A larger announced size throws before anything is read; counted bytes past `maxBytes` end the stream with the error, after at most `maxBytes` bytes. Pausing the subscription pauses the transfer; cancelling it, or `SmartschoolDownload.cancel()`, stops the transfer and closes the connection. Dio keeps reading a streamed answer to its end after its reader cancels, so the client cancels the request itself, as it does when the limit is passed.
  - A download on a session Smartschool refuses logs in and retries as every request: the auth interceptor reads the refused streamed answer (a login-chain page, which it fills in for `/account-verification`), so a login page is never handed over as the file; a retry refused too throws `SmartschoolSessionExpiredError`. A connection that fails halfway through the content ends the stream with a `SmartschoolConnectionError`, the error the request methods throw when Smartschool cannot be reached. Verified live (read-only): a 536,787-byte Intradesk PDF streamed to a temp file with `maxBytes` set to its listing size; `contentLength` and the bytes written matched the listing, `fileName` matched its name, and Intradesk sent no `Content-Encoding` (and its usual `Content-Type: application/x-www-form-urlencoded`).
- Messages: `MessagesService.moveToTrashFrom(msgId, {required boxType, boxId})` moves the copy of a message in the inbox or the sent box to the trash, and names that box (#60). A message the account sends to itself has the same ID in the inbox and in the sent box. `moveToTrash` sends Smartschool's `quick delete`, which names the ID only. Seen live, it moved the inbox copy and left the sent-box copy, which the library could not move. Calling `moveToTrash` again was not safe either: by then the ID is in the trash, and a `quick delete` of a message in the trash deletes it for good (#19). `moveToTrashFrom` sends `postboxes / quickmove messages` with `boxType` (`inbox` or `outbox`), `boxID` (`boxId`, default `0`, for a folder such as the archive), `msgID`, `toBoxType` `trash` and `toBoxID` `0`. Smartschool's web client sends the same when a message of the inbox or the sent box is dragged onto the trash. (Its toolbar's delete button sends `delete messages` with the box. The trash icon of a row sends the `quick delete`, right after showing the message.) This is a move: its source is the inbox or the sent box, never the trash, and its target is the trash. So it may be called while another copy of the ID is in the trash. Verified live (2026-10-01) on messages sent to the own account:
  - moving the sent-box copy put it in the trash and left the inbox copy in the inbox;
  - moving the inbox copy then took it out of the inbox and left the sent-box copy in the trash. The trash lists a message ID once. For a message that had been replied to, the trash still showed the sent-box copy after the inbox copy was moved: its `hasReply` is `false`, while the inbox copy's was `true`.

  Smartschool answers every move with the same acknowledgement without details (a `silent` action), also when it moves nothing (ID `0`, which names no message; see #61 before trying that). So `moveToTrashFrom` returns `Future<void>`: list the boxes to see the outcome. An answer that is not XML throws, as for every command. Another `boxType` (drafts, scheduled, trash) throws an `ArgumentError` before any request. `moveToTrash` is unchanged; its doc now says that it names no box. The live suite (#57) now moves both copies of each of its messages this way, the sent-box copies first, and no longer sends a `quick delete` for them.

### Deprecated
- `MessageSendOptions.requestReadReceipt`, `highPriority` and `extra`, and their constructor parameters (#43): Smartschool's compose form has no field for any of them, so they cannot be sent, and a send that sets one throws an `ArgumentError` (see Fixed below). `MessageSendOptions` itself and `SendMessageParams.options` stay, for the compose form's own options (`lvsCopy` and `sendAt`, #47, see Added above).

### Fixed
- Auth: an XML or form POST on an expired session now logs in again (#8). Smartschool does not redirect such a POST (the XML dispatcher behind `MessagesService.getHeaders()`, `postFormRaw`, …) to `/login`: it answers with a bare `401` and an empty body. The auth interceptor only reacted to landing on the login chain, so it never logged in again, and `postXml` threw `SmartschoolParsingError` ("non-XML response") — `postFormRaw` and the other raw helpers returned an empty string. A `401` now starts the login chain from `/login` (password, 2FA or account verification as needed) and retries the request once, as a GET that is redirected to `/login` already did. A login failure on that path arrives as the matching `SmartschoolAuthenticationError` subtype, like any login triggered by a regular request (see #20 below); a retry that Smartschool still answers with `401` is reported as a `SmartschoolAuthenticationError` — since #5 its subclass `SmartschoolSessionExpiredError`, with the same message — instead of a parsing error.
- Auth: the request that triggered a new login is now accepted when it is retried (#9). With an expired session in the cookie cache, the client logged in again (password and 2FA accepted), but the retry was refused anyway: a GET was redirected to `/login` again (`getJson` threw `SmartschoolAuthenticationError` "Expected JSON but received HTML"), an XML or form POST got a `401` again. The retry copied the headers of the original request, including its `Cookie` header with the refused `PHPSESSID`; `CookieManager` merged that header with the jar and listed the stale session id first, and Smartschool reads the first one. The retry now takes its cookies from the jar only, which holds the new session. Only a new `SmartschoolClient`, which reloads the cookie file, used to work around it.
- Auth: a login failure during a service call is now thrown as itself, not wrapped in a `DioException` (#20). When a regular request finds the session cold or expired, the auth interceptor logs in first; when that login failed, Dio handed the caller a `DioException` with the `SmartschoolAuthenticationError` (or the #11 subtype) as its `error`, so an `on SmartschoolAuthenticationError` / `on SmartschoolInvalidCredentialsError` around `MessagesService(client).getHeaders()` or any other service call never matched — only `ensureAuthenticated()` unwrapped it. The request methods of `SmartschoolClient` (`getJson`, `postJson`, `postXml`, `getRaw`, `postFormRaw`, `postMultipartRaw`, `postFormEncodedRaw`, `download`), and so every service, now throw any `SmartschoolException` that a request failed with as itself. **Behaviour change:** code that caught `DioException` around a service call and read the login failure from its `error` must catch the `SmartschoolAuthenticationError` (or `SmartschoolException`) instead. A network failure is thrown as a `SmartschoolConnectionError` (#21, below); any other `DioException` that carries no `SmartschoolException` is still thrown unchanged, and a request made on `client.dio` directly still gets the wrapped form.
- Auth: `ensureAuthenticated()` no longer reports an unreachable Smartschool as a failed login (#10). A host that does not resolve, a refused or dropped connection, a timeout or a failed TLS handshake — also halfway through the login chain — used to surface as `SmartschoolAuthenticationError('Unable to validate Smartschool session: …')`, with the network error only in the message text, so an app could not tell the user whether to check their network or their password. It is now thrown as a `SmartschoolConnectionError` with the `DioException` as its `cause`. **Behaviour change:** `SmartschoolConnectionError` is deliberately not a `SmartschoolAuthenticationError`, so a `catch` of the authentication error no longer catches a network problem; catch `SmartschoolConnectionError` (or `SmartschoolException`) for that. Other failures of `ensureAuthenticated()` are unchanged.
- Auth: a network failure during a service call is now thrown as a `SmartschoolConnectionError`, as `ensureAuthenticated()` throws it (#21). When Smartschool could not be reached during `MessagesService(client).getHeaders()`, `PresenceService(client).getConfig()` or any other service call, the request methods of `SmartschoolClient` (`getJson`, `postJson`, `postXml`, `getRaw`, `postFormRaw`, `postMultipartRaw`, `postFormEncodedRaw`, `download`) let the raw `DioException` through, so an `on SmartschoolConnectionError` (or `on SmartschoolException`) around a service call missed it and the app had to classify the `DioException` itself. The same failures as for #10 — a host that does not resolve, a refused or dropped connection, a timeout, a rejected certificate or failed TLS handshake, also halfway through a login the call triggered — are now thrown as a `SmartschoolConnectionError` with the `DioException` as its `cause` and the same message as from `ensureAuthenticated()`. **Behaviour change:** code that caught `DioException` around a service call to detect a network problem must catch `SmartschoolConnectionError` (or `SmartschoolException`) instead; the `DioException` is still available as its `cause`. Other `DioException`s are still thrown unchanged, and a request made on `client.dio` directly still gets the plain `DioException`.

Smartschool's web client opens the same URL as a plain page navigation (`document.location.href`), and the Python reference returns the answer's bytes as they are. The docs of `download` and `downloadStream` now say that both hand over the file itself, and that the `contentType` of the stream does not tell the type of the file. No behaviour change.
- Session: a `SmartschoolClient` used after `dispose()` now says so, instead of reporting Smartschool as unreachable (#54). The closed Dio client refuses a request with a connection error of its own ("Dio can't establish a new connection after it was closed"), which the request methods have reported since #21 (7984957) as a `SmartschoolConnectionError` ("Unable to reach Smartschool at …: the connection failed"), so an app that shows "offline" or retries on that error did so for a client it had disposed itself; and `emitNotificationCounterUpdate` threw a `StateError` ("Cannot add new events after calling close"), where its doc promised `true` or `false`. Now:
  - every request method (`getJson`, `postJson`, `postXml`, `getRaw`, `getResponse`, `postFormRaw`, `postFormResponse`, `postMultipartRaw`, `postMultipartResponse`, `postFormEncodedRaw`, `download`, `downloadStream`), and so every service call, as well as `ensureAuthenticated()`, `platformId`, `authenticatedUser` and `getCurrentUser()`, throws a `StateError` ("SmartschoolClient was disposed: …") on a disposed client, before it sends anything, also when it has the answer cached (`ensureAuthenticated()` after a successful one used to complete without a request). A request that was running when the client was disposed and does not complete, such as one cut off by a forced `dispose()` or one whose login the closed client refused, fails with it too ("SmartschoolClient was disposed during GET …"), and so does the stream of a download that was being read. On a disposed client, no failure is classified as a network failure anymore. The error is deliberately not a `SmartschoolException`: using a disposed client is a mistake in the app, not a problem of the network or of Smartschool; create a new client to use Smartschool again;
  - `emitNotificationCounterUpdate` returns `false` and emits nothing on a disposed client, as the README already said ("returns `false` if the stream is already closed"): the stream is closed, so no listener can get the update, and a source that publishes updates as they come in (a websocket listener, a polling loop) may well get one more in after the app disposed the client, which is no reason to throw at it;
  - `dispose()` can be called again: a later call does nothing and returns what the first call returned (its `force` is ignored); it closed the Dio client again before.

  **Behaviour change:** a request on a disposed client throws a `StateError` instead of a `SmartschoolConnectionError`, and an `on SmartschoolException` clause does not catch it.
- Auth: the doc of `SmartschoolInvalidCredentialsError` (and its row in the README's Exceptions table) now says that in rare cases it can also mean a rejected login form token (`login_form[_token]`) rather than wrong credentials (#46). Smartschool answers both with the same page (back on `/login`, the same "Ongeldige inloggegevens." error, the username kept), so the login cannot tell them apart; since #45 the login posts the token of a form it loaded itself in a new session, so this should be rare. Do not log in again automatically on this error: every rejected login brings the account closer to being locked. Documentation only, no behaviour change.
- Messages: `MessagesService.moveToTrash` now returns `null` when Smartschool deletes nothing, as documented for an answer that is not a `finish quick delete` (#59). Smartschool answered such a `quick delete` with an empty body (seen live by the live suite of #57, for `moveToTrash(0)`: ID `0` names no message; but not always, and a `quick delete` is never a guaranteed no-op, see #61), which `SmartschoolClient.postXml` rejected as not XML: `moveToTrash` threw a `SmartschoolParsingError` ("Smartschool returned a non-XML response for "quick delete" …:", with nothing after the colon), so a caller could not tell that nothing was deleted from a broken answer. `postXml` has a new optional parameter `allowEmptyAnswer` (default `false`), which `moveToTrash` sets: an empty answer (no body, or white space only) with status `200` then returns no elements. Only with status `200`: on an expired session Smartschool refuses an XML POST with an empty `401` (#8), which the client still never reads as an answer (it logs in again and retries the command, or throws a `SmartschoolSessionExpiredError`). An empty answer with another status, an HTML page (`SmartschoolAuthenticationError`) and other text that is not XML (`SmartschoolParsingError`) still throw, for `moveToTrash` too, and every other command still rejects an empty answer. Whether Smartschool answers the same for the ID of another user's message was not checked (and is not to be tried live with a message in the trash: that deletes it for good). **Behaviour change:** `moveToTrash` returns `null` where it threw a `SmartschoolParsingError`.
- Messages: the doc of `MessagesService.moveToTrash` (and its README row) now warns that it is never a guaranteed no-op, and that callers should prefer `moveToTrashFrom`, which names the box (#61). Smartschool's `quick delete` names the ID only: Smartschool acts on whichever copy of the ID its own session state points to, which the caller does not control. That can be a copy in the trash, and a `quick delete` of a message in the trash deletes it for good (#19). Seen live (2026-10-01): a `quick delete` of ID `0`, which names no message, was answered with an empty body twice, and later in the same session (after a `quickmove messages` of ID `0` to the trash and read-only requests of the boxes) with a `finish quick delete` with `boxType` `trash` and an empty `status`: the answer to a `quick delete` of a message in the trash. ### Added
